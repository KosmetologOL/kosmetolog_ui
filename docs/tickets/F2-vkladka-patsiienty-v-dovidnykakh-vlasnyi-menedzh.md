## Контекст

Адмін-вкладка «Пацієнти» (Довідники) зараз — тонка обгортка PatientManager над загальним CRUDManager, який викликає GET /patients БЕЗ query-параметрів. Бекенд (patient.controller.ts:13) за замовчуванням віддає limit=10, тож адмін бачить лише 10 останніх пацієнтів: лічильник «Усього» бреше, клієнтський пошук фільтрує тільки ці 10, редагування й видалення решти пацієнтів недоступні взагалі. Наївний фікс «limit=100000» не годиться — бекенд для кожної сторінки рахує getLastVisitMap по звітах, і повний список навантажив би БД. Ендпоінт уже підтримує page/limit/query — треба просто використати його, як це робить реєстр PatientList. Окрема проблема того ж місця: підтвердження видалення пацієнта показує генеричне «Ви впевнені, що хочете видалити цей запис?» — без ПІБ і без попередження, що рекомендаційний лист пацієнта стане недосяжним (бекенд видаляє лише Patient, Report лишається сиротою), а бекапів БД немає — помилкове видалення незворотне.

## Кроки реалізації

1. Винести хелпер getPageItems із frontend/src/components/PatientList/PatientList.tsx:16–28 у новий файл frontend/src/lib/pagination.ts (export const getPageItems = …) і імпортувати його в PatientList.tsx через #lib/pagination.
2. Повністю переписати frontend/src/components/PatientList/PatientManager.tsx: замість обгортки над CRUDManager — самостійний компонент. Проп `canDelete` зберегти (ReferencePanel.tsx:204 передає canDelete={isAdmin}).
3. Стан: page, query + `const debouncedQuery = useDebouncedValue(query, 400)`, patients, total, totalPages, isLoading, hasError, editingPatient (IPatient | null), deletingPatient (IPatient | null), isDeleting. PAGE_SIZE = 20.
4. Фетч за зразком PatientList.tsx:45–74: `patientsApi.getAllPatients(page, PAGE_SIZE, debouncedQuery, { signal })` з AbortController в useEffect, `axios.isCancel` для скасованих запитів, setHasError(true) у catch. При зміні debouncedQuery скидати page на 1.
5. UI в стилі довідників: заголовок `<h2 className="panel-title">Пацієнти</h2>` + підпис «Усього: {total}» (тепер це реальний total із сервера); поле пошуку з іконкою і кнопкою очищення — розмітку взяти з CRUDManager.tsx:378–397; рядки списку — .list-row з fullName та діями «Редагувати» (btn btn-ghost btn-sm) і «Видалити» (btn btn-danger-soft, лише якщо canDelete); пагінація — розмітка з PatientList.tsx:224–265 з getPageItems.
6. Стани списку: скелетони при isLoading; при hasError — екран «Не вдалося завантажити… [Спробувати ще раз]» за зразком PatientList.tsx:164–175; при порожньому результаті — «Нічого не знайдено за запитом …» / «Записів ще немає».
7. Редагування: наявний PatientFormModal (як у PatientList.tsx:279+) → patientsApi.updatePatient → toast.success("Дані пацієнта оновлено.") → refetch.
8. Видалення: ConfirmModal з message `Видалити картку пацієнта «${deletingPatient?.fullName}»? Разом із нею стане недоступним її рекомендаційний лист. Дію неможливо скасувати.`, isDanger, isLoading={isDeleting}, loadingLabel="Видаляємо…"; onConfirm → patientsApi.deletePatient(deletingPatient._id) → toast.success("Картку пацієнта видалено.") → refetch.
9. Переконатися, що PatientManager більше не імпортує CRUDManager і createReferenceApi.

## Критерії приймання

- [x] Вкладка «Пацієнти» показує пацієнтів посторінково (20 на сторінку) з робочою пагінацією; «Усього» дорівнює реальній кількості пацієнтів у БД, а не 10.
- [x] Пошук виконується на сервері (параметр query) і знаходить пацієнта, якого немає на першій сторінці; при зміні запиту сторінка скидається на 1.
- [x] Редагувати і видалити можна будь-якого пацієнта з будь-якої сторінки; кнопка «Видалити» видима лише адміну.
- [x] Підтвердження видалення містить ПІБ пацієнта і попередження про недоступність рекомендаційного листа; кнопка підтвердження показує стан «Видаляємо…».
- [x] Жоден запит не тягне повну колекцію пацієнтів (limit завжди обмежений).
- [x] При падінні запиту показується екран помилки з кнопкою «Спробувати ще раз», а не «Записів ще немає».

## Ручна перевірка

> У проєкті немає тест-сьюти — перевірка виконується вручну на локальному дев-середовищі. Жодних дій проти продакшн-БД.

1. Локально переконатися, що в dev-БД більш ніж 20 пацієнтів (за потреби створити кілька ТЕСТОВИХ через «Новий пацієнт» у реєстрі).
2. Зайти адміном у Довідники → Пацієнти: перевірити лічильник «Усього», перегортання сторінок, пошук за прізвищем пацієнта з другої сторінки.
3. Відредагувати ПІБ тестового пацієнта — тост і оновлений список.
4. Видалити СТВОРЕНОГО ТЕСТОВОГО пацієнта (не реальний запис!): у модалці видно його ПІБ і попередження про лист.
5. У DevTools → Network переконатися, що запити мають page/limit/query і не тягнуть усю колекцію.
6. Зупинити backend і відкрити вкладку — екран помилки з retry-кнопкою.
