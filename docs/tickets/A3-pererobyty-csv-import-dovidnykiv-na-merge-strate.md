# A3 · Переробити CSV-імпорт довідників на merge-стратегію з авто-знімком і видаленням зайвого наприкінці

| Пріоритет | Оцінка | Епік | Залежить від |
|---|---|---|---|
| **P1** | M (1–2 дні) | Безпека даних | A2 |

## Контекст

Імпорт CSV у довідниках (обстеження, засоби, процедури, спеціалісти — через CRUDManager, та записи категорій — через CategoryItemsManager) працює за схемою «спершу видалити ВСІ наявні записи, потім створити нові з файлу»: handleConfirmImport у frontend/src/components/CRUDManager.tsx:249–316 (фаза deleting → фаза creating) і дзеркально у frontend/src/components/Admin/CategoryItemsManager.tsx:233–277. Якщо на фазі створення обривається мережа/сесія або падає один запис — довідник лишається частково чи повністю порожнім, і відновити його нізвідки: бекапів БД немає, а вихідний CSV міг бути неповним. Порядок пояснено unique-індексом за name (є в ExamSchema/MedicationSchema/ProcedureSchema), але сусідній HomeCaresManager.tsx:256–290 уже давно робить безпечний merge (update за збігом назви, create для нових) — підхід треба вирівняти. Бонус: зникає подвійний обсяг запитів (зараз 300 рядків = ~600 HTTP-запитів delete+create).

## Кроки реалізації

1. У CRUDManager.tsx (frontend/src/components/CRUDManager.tsx) переписати handleConfirmImport (рядки 249–316) за схемою «знімок → merge → зачистка», зберігши наявний runInBatches (рядки 24–40, пачки по 15):
2. Крок 3.1 — авто-знімок: першим рядком тіла (після `if (!pendingImport) return;`) викликати наявний `handleExportCsv();` (оголошений на рядку 182) — CSV поточного стану падає в Завантаження ще до будь-яких мутацій.
3. Крок 3.2 — дедуплікація файлу: перед merge звести pendingImport до унікальних нормалізованих назв (`name.trim().toLowerCase()`, лишати останній рядок-дублікат); якщо дублікати були — показати toast-попередження (`Пропущено N дублікатів назв у файлі.` через plural). Без цього два однакові рядки з файлу впадуть на unique-індексі при create.
4. Крок 3.3 — фаза merge (замість deleting+creating): для кожного row знайти existing у list за нормалізованою назвою; якщо знайдено — `api.update(existing._id!, payload)`, інакше — `api.create(payload)` (payload лишити як зараз: `hasRecommendation ? { name, recommendation } : { name }`). Виконувати через runInBatches із прогресом. Це обходить unique-індекс без жодного видалення.
5. Крок 3.4 — фаза зачистки ОСТАННЬОЮ: тільки після повного успіху merge видалити через runInBatches старі записи, чиїх нормалізованих назв немає у файлі (`api.remove(item._id!)`). Якщо merge впав — до видалень справа не доходить і довідник лишається повним.
6. Крок 3.5 — оновити стани/тексти: тип importProgress (рядки 79–81) з фаз "deleting" | "creating" на "merging" | "cleanup"; loadingLabel модалки (рядки 523–529) → «Оновлюємо записи… X/Y» і «Видаляємо відсутні у файлі… X/Y»; message модалки підтвердження (рядок 519) → «Записи з наявними назвами буде оновлено, нові — додано; записів, відсутніх у файлі (N), буде видалено після успішного імпорту.» (N порахувати з list і pendingImport); catch-toast (рядки 308–310) → «Під час імпорту сталася помилка. Наявні записи не видалялися, частина могла оновитися — перевірте список і повторіть імпорт.»; success-toast (рядки 300–305) → «Імпортовано N записів: оновлено X, додано Y, видалено Z.» Застарілий коментар про порядок delete-then-create (рядки 252–255) замінити на опис merge-стратегії.
7. Дзеркально переписати handleConfirmImport у frontend/src/components/Admin/CategoryItemsManager.tsx (рядки 233–277): знімок через handleExportCsv (рядок 177), merge через updateCategoryItem/createCategoryItem за збігом назви в items, зачистка через deleteCategoryItem наприкінці; ті самі правки текстів модалки (рядок 514) і тостів (рядки 261–271).
8. Бекенд-ендпоінт bulk-replace свідомо ПОЗА скоупом цього тікета: merge + наявний батчинг по 15 прибирає деструктивну фазу і зменшує кількість запитів з ~2N до N + кількість реально видалених.
9. Запустити `npm run lint` у frontend/ після правок.

## Критерії приймання

- [ ] В імпорті немає фази попереднього повного видалення: обрив мережі/помилка на будь-якому кроці не лишає довідник порожнім (наявні записи максимум частково оновлені).
- [ ] Перед будь-якими мутаціями автоматично зберігається CSV-знімок поточних записів у Завантаження.
- [ ] Записи, відсутні у файлі, видаляються лише після успішного завершення фази оновлення/створення.
- [ ] Повторний імпорт того самого файлу ідемпотентний: кількість записів не змінюється, дублікати не виникають (у т.ч. для файлів із дубльованими назвами).
- [ ] Для файлу з N рядків без видалень виконується ~N запитів мутації замість ~2N.
- [ ] Поведінка CRUDManager і CategoryItemsManager ідентична, тексти модалки/тостів українською відповідають новій логіці (записи «оновлено/додано/видалено»).

## Ручна перевірка

> У проєкті немає тест-сьюти — перевірка виконується вручну на локальному дев-середовищі. Жодних дій проти продакшн-БД.

1. ТІЛЬКИ на локальній БД: підняти локальний mongod, запустити бекенд як `MONGODB_URI="mongodb://127.0.0.1:27017/kosmetology_dev" npm run dev` (не чіпати backend/.env з прод-URI), наповнити довідник сідером з A2 або вручну; фронтенд — `npm run dev`.
2. Сценарій merge: експортувати довідник «Обстеження» у CSV; у файлі змінити рекомендацію одного запису, додати новий рядок, видалити один наявний; імпортувати → змінений оновлено (той самий _id — перевірити, що редагування не перетворилося на delete+create, наприклад через Network-таб: PUT, а не DELETE+POST), новий додано, видалений зник, у Завантаженнях зʼявився файл-знімок.
3. Сценарій обриву: почати імпорт великого файлу і посеред фази «Оновлюємо записи…» увімкнути Offline у DevTools → Network → зʼявляється toast про помилку, список НЕ порожній, жоден запис не видалено.
4. Сценарій дублікатів: файл із двома рядками з однаковою назвою → попередження про дублікати, імпорт завершується без помилки unique-індексу.
5. Повторити merge-сценарій для категорії в CategoryItemsManager (адмін-розділ категорій).
6. Двічі поспіль імпортувати той самий файл → кількість записів у довіднику не змінюється.
7. `cd frontend && npm run lint` та `npm run build` — без помилок.
