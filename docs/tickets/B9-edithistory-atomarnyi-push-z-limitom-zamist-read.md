# B9 · editHistory: атомарний $push з лімітом замість read-modify-write

| Пріоритет | Оцінка | Епік | Залежить від |
|---|---|---|---|
| **P2** | S (до пів дня) | Шлях збереження листа | B8 |

## Контекст

update() у reports.service.ts оновлює історію редагувань у два кроки: findById читає документ, у памʼяті збирається масив [...existing.editHistory, новийЗапис], і findByIdAndUpdate перезаписує масив цілком. Два одночасні PUT (наприклад, дві вкладки) прочитають однакову історію — другий перезатре запис першого. Крім того, editHistory нічим не обмежений (ReportSchema.ts:153), росте вічно і цілком повертається клієнту в кожному GET звіту та рендериться повним списком у формі. Виправлення — атомарний $push з $each/$slice: MongoDB сам допише запис і обріже масив до останніх 50 без гонки. Читання existing у update() лишається — воно потрібне для знімка ревізії з тікета B8 (тому цей тікет виконувати після B8, обидва переписують те саме місце).

## Кроки реалізації

1. У backend/src/services/reports.service.ts в update() видалити блок збирання масиву в памʼяті (рядки 151–154 у поточній версії файлу; після B8 номери зсунуться):
```ts
  const editHistory = [
    ...(existing.editHistory || []),
    createHistoryItem("update", actor),
  ];
```
2. Замінити виклик findByIdAndUpdate (рядки 156–163) на атомарний запис:
```ts
  return Report.findByIdAndUpdate(
    id,
    {
      $set: reportData,
      $push: {
        editHistory: {
          $each: [createHistoryItem("update", actor)],
          $slice: -50,
        },
      },
    },
    { new: true },
  );
```
(ліміт 50 — узгоджене число з аудиту; контролер уже обробляє null → 404, семантика не змінюється).
3. Опційно (за рекомендацією аудиту): у getById і getByPatientId додати проєкцію другим аргументом — `Report.findById(id, { editHistory: { $slice: -20 } })` та `Report.findOne({ patient: patientId }, { editHistory: { $slice: -20 } })` — GET перестає тягнути всю історію; $slice-проєкція не виключає решту полів документа.
4. Виконати `npm run build` у backend/.

## Критерії приймання

- [ ] Після кожного успішного PUT в editHistory додається рівно один запис «update»; масив у документі ніколи не перевищує 50 елементів.
- [ ] Два конкурентні PUT залишають в історії ОБИДВА записи (жоден не губиться).
- [ ] PUT для неіснуючого id повертає 404 (поведінка контролера не змінилася).
- [ ] Секція «Історія редагувань» у формі листа працює як раніше.

## Ручна перевірка

> У проєкті немає тест-сьюти — перевірка виконується вручну на локальному дев-середовищі. Жодних дій проти продакшн-БД.

1. Локально: зберегти лист тестового пацієнта кілька разів; після F5 у секції «Історія редагувань» зʼявляються нові записи «Оновлення» з правильним користувачем/часом.
2. Конкурентність: відкрити лист у двох вкладках і натиснути «Зберегти лист» майже одночасно; після F5 в історії два нові записи.
3. Read-only перевірка ліміту в mongosh: db.reports.findOne({ _id: ObjectId("<reportId>") }, { editHistory: 1 }) — довжина масиву ≤ 50.
4. curl PUT з вигаданим id → 404 «Звіт не знайдено».
