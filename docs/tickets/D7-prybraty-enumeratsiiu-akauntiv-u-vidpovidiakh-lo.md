# D7 · Прибрати енумерацію акаунтів у відповідях login

| Пріоритет | Оцінка | Епік | Залежить від |
|---|---|---|---|
| **P2** | S (до пів дня) | Автентифікація і безпека | D5 |

## Контекст

Тексти помилок логіна розкривають стан акаунта стороннім: для email із pending-заявкою login повертає «Запит на реєстрацію очікує підтвердження» (auth.service.ts, гілка if (!user) з пошуком у RegistrationRequest), тоді як для неіснуючого — «Неправильний email або пароль». Перебором email можна дізнатися, хто зареєстрований чи подав заявку. Rate-limit (10 логінів/15 хв) стримує масовий перебір, тож для внутрішнього продукту клініки це low-ризик, але вирівняти тексти login дешево: стан «очікує підтвердження» користувач і так бачить у потоці реєстрації («Запит на реєстрацію вже існує» при повторній подачі). Повідомлення register свідомо лишаємо як є — нейтралізувати їх без email-розсилки означало б зламати UX реєстрації; це фіксується коментарем у коді як усвідомлений компроміс.

## Кроки реалізації

1. У backend/src/services/auth.service.ts у login() замінити гілку if (!user) { const pending = await RegistrationRequest.findOne({ email }); if (pending) throw …(«Запит на реєстрацію очікує підтвердження»); throw …(«Неправильний email або пароль»); } на єдиний рядок: if (!user) throw ApiError.badRequest("Неправильний email або пароль"); (якщо D5 ще не влито — throw new Error з тим самим текстом).
2. Видалити тепер невикористаний імпорт RegistrationRequest (рядок «import RegistrationRequest from "../models/RegistrationRequest";» посеред файлу — використовувався лише в цій гілці).
3. Над register() (auth.service.ts) і createRegistrationRequest (registrationRequests.service.ts) додати короткий коментар: // Тексти «вже існує» розкривають наявність акаунта — усвідомлений компроміс для внутрішнього продукту: без них реєстрація стає німою, перебір стримує rate-limit (10/год).
4. Фронтенд не чіпати: LoginForm просто показує message із сервера.

## Критерії приймання

- [ ] POST /auth/login для неіснуючого email, для email із pending-заявкою і для існуючого email з неправильним паролем повертає ідентичну відповідь «Неправильний email або пароль» (однаковий статус і текст)
- [ ] Потік реєстрації досі інформативний: повторна подача заявки → «Запит на реєстрацію вже існує», зайнятий email → «Користувач вже існує»
- [ ] Імпорт RegistrationRequest у auth.service.ts видалено; npm run build проходить
- [ ] Компроміс щодо текстів register задокументовано коментарем у коді

## Ручна перевірка

> У проєкті немає тест-сьюти — перевірка виконується вручну на локальному дев-середовищі. Жодних дій проти продакшн-БД.

1. Локальна тестова БД, npm run dev. Створити pending-заявку: curl -s -X POST http://localhost:5000/auth/register -H 'Content-Type: application/json' -d '{"email":"pending@test.local","password":"secret1","role":"doctor","name":"Тест Лікар"}'.
2. curl -s -X POST http://localhost:5000/auth/login -d '{"email":"pending@test.local","password":"secret1"}' -H 'Content-Type: application/json' → «Неправильний email або пароль» (раніше — «Запит на реєстрацію очікує підтвердження»).
3. Той самий запит з email nobody@test.local → байт-у-байт однакова відповідь.
4. Повторний register для pending@test.local → «Запит на реєстрацію вже існує» (потік реєстрації не постраждав).
